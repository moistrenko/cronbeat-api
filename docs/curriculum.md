# Учебная программа: синьор-фронт + фулстек

Три цели, которые должны сойтись в одном проекте:

1. Довести фронтенд до уровня, на котором тебя можно нанимать как синьора:
   JavaScript, TypeScript, React, архитектура UI, тесты, доступность,
   производительность, паттерны.
2. Выучить бэкенд как ремесло, а не «фронтендер с CRUD»: PHP, Laravel,
   SQL, очереди, эксплуатация.
3. Закрыть дыры, которые валят собеседования независимо от стека:
   как работает веб, алгоритмы, системный дизайн на пальцах.

Cronbeat — полигон, а не отдельный «учебный задачник». Каждая тема сначала
попадает в продукт, и только если продуктом её не закрыть (алгоритмы,
часть паттернов) — идёт отдельным упражнением.

## Честное ограничение

Синьор — это не сертификат и не пройденный плейлист. Это глубина решений
плюс привычка объяснять trade-off. За 10–15 часов в неделю за год можно
**закрыть синьорский силлабус и натренировать объяснение**. Сам титул
появится, когда ты год принимал решения в проде и можешь рассказать,
почему сделал так, а не иначе.

Поэтому мы не учим «всё сразу». У спринта по-прежнему одна главная
практическая тема. Фронт, бэк и теория крутятся вокруг неё. Алгоритмы —
единственный трек, который идёт отдельно: дашборд мониторинга сам по себе
не научит тебя деревьям и сложности.

## Бюджет времени (10–15 часов в неделю)

| Кусок | Часы | Зачем |
| --- | --- | --- |
| Продукт (код спринта) | 7–10 | Основной навык |
| Теория и письменные ответы | 1–2 | Собеседования |
| Алгоритмы (1–2 задачи) | 1–2 | Скрининги и «подумай вслух» |

Если неделя рваная — режь алгоритмы, не продукт. Продукт даёт переносимые
навыки, LeetCode без них быстро забывается.

## Три трека

### Трек A — продукт (фронт и бэк вместе)

Вертикальные срезы. Фронт не ждёт «когда бэк закончится». С третьего
спринта почти в каждом спринте есть задача и в `cronbeat-web`, и в
`cronbeat-api`.

Синьорский фронт в этом треке — не «красивые кнопки», а решения:

- как устроен слой данных (TanStack Query, кэш, инвалидация, оптимизм);
- как не размазать состояние по десяти контекстам;
- как типизировать API так, чтобы бэк и фронт не врали друг другу;
- как тестировать то, что ломается у пользователя, а не реализацию хука;
- как не убить доступность и производительность по дороге.

Бэкенд в этом треке — PHP как язык (типы, ООП, исключения, пакеты) плюс
Laravel как канон зрелого фреймворка.

### Трек B — фундамент и собеседования

Письменные ответы, как уже заведено в [fundamentals.md](fundamentals.md).
Сюда же входят JS/TS «под капотом» и паттерны: не энциклопедия GoF,
а те, которые ты обязан узнать в лицо на ревью и на собесе.

### Трек C — алгоритмы

Каждую неделю 1–2 задачи. Цель не «решить 300 easy», а научиться:

- оценить сложность вслух;
- выбрать структуру данных до кода;
- разобрать крайние случаи;
- написать чисто на TypeScript, потом объяснить.

Площадка: LeetCode или аналог, язык TypeScript. PHP подключится позже,
когда синтаксис перестанет мешать думать.

## Карта: что считается «синьорским фронтом» в Cronbeat

К релизу (спринт 10) этого ещё не будет целиком — синьорский слой
добирается спринтами 11–16. Без этого списка легко скатиться в
«ещё один CRUD на хуках».

| Навык | Где проявится в продукте |
| --- | --- |
| JavaScript: область видимости, замыкания, this, прототипы, event loop | Любой клиентский код; модуль теории 5 и JS-модули |
| TypeScript: дженерики, discriminated unions, narrowing, utility types | Клиент API, формы, статусы проверок |
| React: композиция, мемоизация по делу, порталы, error boundaries | Дашборд, формы, тосты ошибок |
| Состояние сервера vs UI | TanStack Query + локальный UI-стейт |
| Формы и валидация | React Hook Form + Zod, те же схемы, что на бэке |
| Маршрутизация и защита экранов | Роутер, layout, редирект неавторизованных |
| Дизайн-система на компонентах | Кнопки, статусы, таблицы без копипасты |
| Тесты | Vitest + Testing Library на критичные потоки |
| Доступность | Клавиатура, фокус, роли, контраст |
| Производительность | Виртуализация списка истории, мемо, бандл |
| Наблюдаемость фронта | Ошибки, аналитика на лендинге |
| Архитектура | Слои `ui` / `features` / `entities` / `shared`, без религии FSD |

Vue-привычки разбираем на ревью каждый раз, когда всплывут: мутации
пропа, «магическая» реактивность, `watch` вместо вычисляемого значения,
эффекты, которые синхронизируют то, что должно быть производным.

## Паттерны: какие учим, какие нет

Учим те, без которых синьор выглядит пусто, и те, которые реально всплывут
в коде Cronbeat. Не учим коллекцию из 23 названий ради викторины.

**Обязательные (и фронт, и бэк):**

- Композиция вместо глубокого наследования.
- Стратегия — каналы уведомлений (Telegram / почта / Slack) с одним контрактом.
- Наблюдатель / подписка — TanStack Query, события Laravel, вебхуки.
- Адаптер — внешние API (Telegram) за своим интерфейсом.
- Фасад — тонкий контроллер, толстый сервис предметной области.
- Репозиторий — осторожно: в Laravel часто хватает Eloquent; вводим,
  когда запросы начинают размножаться.
- Состояние — статусы проверки (waiting / late / paused), явная машина
  состояний, а не россыпь булевых флагов.
- Декоратор / middleware — пайплайн HTTP.
- Модуль / слои — границы фич на фронте.

**Паттерн считается выученным**, когда ты применяешь его в PR и в двух
предложениях объясняешь, какую проблему он закрыл и чем был бы хуже
альтернативный вариант. Название без применения не засчитывается.

## Алгоритмы: программа на год, не на спринт 0

Порядок специально «от собеседований», а не от олимпиад.

1. Сложность O-нотации, массивы, хэш-таблицы, два указателя.
2. Строки, стек, очередь.
3. Связный список (на собесах любят, в проде редок).
4. Бинарный поиск.
5. Деревья: обход, BST.
6. Куча / приоритетная очередь — пригодится, когда будем думать
   про «кто просрочил».
7. Графы: BFS/DFS — в продукте слабо, на собесах часто.
8. Динамика: только базовые постановки (не 50 задач на каждую схему).
9. Сортировки: не писать quicksort с нуля каждый день, но понимать
   стабильность и когда `n log n`.

Формат недели: одна задача medium или две easy. Решение в
`docs/katas/` или отдельном файле — как удобнее, главное чтобы я мог
разобрать рассуждение, а не только Accepted.
